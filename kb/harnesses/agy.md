# Antigravity (`agy`)

Meridian hosts `agy` through a plugin and never runs it. The user starts Google Antigravity's own TUI, by hand or with the command `meridian agy` prints, and the plugin Mars installs into `.agy/` (hooks, an MCP server, Meridian's skills) registers the session, carries Meridian's guidance and messages in, and lets the session spawn agents on other harnesses. Antigravity's terms forbid running `agy acp` as a backend worker under a personal Google sign-in, which is the sign-in in use, so spawning `agy` waits until the terms change ([#1016](https://github.com/haowjy/meridian-cli/issues/1016)). Mars carries the same fact: routing never picks `agy`, and Mars writes `.agy` agent files and a host's provided content even when Meridian manages routing ([targets](../mars/package-management.md#targets)).

What the session can and can't do: the source checkout's `docs/antigravity.md`. How the adapter is built (plugin-hosted harnesses, the hook, the server, the watcher): `src/meridian/lib/harness/AGENTS.md`, "`agy/` is hosted by its plugin". How `.agy` is laid out and how `agy` treats hooks and MCP servers: mars-agents `docs/config/mcp-and-hooks.md`, "Antigravity".

## Waking an idle session

`agy` offers no way for an outside process to put input into a running conversation, and Meridian doesn't type into the user's terminal. The one thing that starts a model call with nothing typed is a background command the agent started: when it exits, `agy` wakes the agent with its exit code and stdout. So the plugin's `Stop` hook asks the model to keep one such command running, `meridian harness-watch agy`, which exits when a message arrives for an idle session. A message to a session mid-turn is not a reason to wake: it reaches the model at the turn's next model call through `PreInvocation`.

Delivery is confirmed once per turn, at `Stop`, by finding the message's `[meridian:<id>]` marker in the transcript. Confirming at `PreInvocation`, which fires on every model call, would start Python and read the whole transcript on each call while a message is in flight. Confirming at `Stop` works because `agy` writes the injected step before the model call it rides on (below). A message whose marker is missing goes back to the inbox, and the watcher wakes the session to deliver it again instead of waiting for the user to type. How claim and confirm work: `src/meridian/lib/harness/AGENTS.md`, `inbox.py`.

The watcher is the one wake mechanism: Meridian's own prompts (the state reminder and keepwarm pings, below) are queued in the conversation's session inbox with no sender and wake the session like any message, instead of through a second thing the model must keep running. Claude's idle mod likewise injects every prompt through one mechanism.

Its costs: every session shows `1 task(s)` for its life, the first turn and each wake end with one extra continuation to restart the watcher, and starting it is a shell command that `agy` may ask to approve unless the user allows `command(meridian)`.

**A message sent after Esc waits until the user types.** After any Esc, during a reply or a tool call, `agy` starts no model call for a finished background command until the user types, and a later background exit doesn't restore it ([#1051](https://github.com/haowjy/meridian-cli/issues/1051)). So the watcher exits for a message only once the plugin's `busy` mark is gone (`PreInvocation` sets it, `Stop` clears it), and Esc fires no `Stop`, so after Esc the message waits for the next typed prompt and reaches the model in that turn. A watcher that exited on the cancel would only put its stdout on screen: tried live, it exited and no model call followed. Only the idle sensor reads the cancel. If `agy` starts waking after a cancel, the watcher can read the cancel too.

## Idle notices

An `agy` primary gets Meridian's idle push, cache warning and state reminder, on `[harness.agy.idle]` config like Claude's. User guidance: the source checkout's `docs/antigravity.md` and `docs/configuration.md`; the idle core's contract: [idle notifications](../spawns/idle-notifications.md).

- **The sensor runs in the plugin's MCP server**, one per conversation the server holds, because that server lives exactly as long as the `agy` process. A typed prompt (a `USER_INPUT` step from `USER_EXPLICIT` in the transcript) is the user's return; a watcher wake or hook-injected text is not, so a wake doesn't send a second push.
- **Esc is read from the conversation's database.** `agy` fires no hook on Esc, so the sensor reads the `executor_metadata` table (below): when it sees `busy` touched it records the table's highest row index, and a later `USER_CANCELED` row ends the turn. It beat the other two signals `agy` leaves: the CLI log line `Cancelling in-progress response for conversation <id>` is unstructured text found through `/proc`, which is Linux-only, and the transcript's step status can't tell a cancel from a long silent generation.
- **Any read that fails counts as a running turn.** An unreadable database, a baseline not yet recorded or an unreadable transcript gives no turn end. The cost is a missed notice for that stretch, never a notice while the session works. The sensor polls once a second, so an Esc that lands before it records the baseline falls inside the baseline and is missed.
- **A 30-minute default TTL, tuned per model by the user.** Google publishes no window, and it differs by model: Neon Medium held across 55- and 65-minute idle gaps, while `gemini-3.8-flash-low` lost its cache within 55 minutes ([Antigravity cache](../research/prompt-cache-retention.md#antigravity)). The sensor can't tell which model a session runs, so one default serves all of them: `ttl_seconds = 1800`, as Codex has, which puts the cache warning, and with it the state reminder and ping 1, about 20 minutes after a turn at the global 10-minute lead. Too long a TTL sends the warning and pings onto a cache that is already cold; too short only warns early. A Neon user can set `[harness.agy.idle] ttl_seconds = 3600`, and the owner, who runs Neon, does. Google's server changes alone have moved hit rates sharply before, so any number is an estimate.
- **The state reminder is a message in the conversation's session inbox.** When the warning fires and the session has a work item, the sensor queues the reminder with no sender, and the watcher wakes the session to deliver it like any message, so no agy-specific path enters the idle core. It is queued only while a watcher runs: only the watcher wakes an idle `agy` session, and without one the reminder would wait and land in the user's next typed prompt, telling them they are away. It offers no `compact-now` (below), and offers `stop-waiting` only when keepwarm is on, as on Claude.
- **Keepwarm: opt-in, off by default.** With it on, ping 1 goes out at the cache warning (the state reminder takes its slot when there is a work item) and later pings one lead after each turn end, up to `keepwarm_pings`, with the Claude mod's stopping rules ([keepwarm pings](../spawns/idle-notifications.md#keepwarm-pings-claude)). It is worth having because the window is long: on a 30-minute window a ping falls due about every 20 minutes, each a cached call that costs less than the uncached re-read of the whole context a return to a cold cache pays. It stays off by default because each ping spends about two model calls of `agy`'s usage quota, the resource that is short. A global `[idle] keepwarm = true` turns it on for `agy` too, because keepwarm is one preference about the provider's cache, not a per-harness feature. How the sidecar times the pings and the sensor delivers them: `src/meridian/lib/idle/.context/CONTEXT.md` and `src/meridian/lib/harness/AGENTS.md`.
- **A ping turn isn't kept read-only.** `agy`'s `PreToolUse` hook could deny tools, but its deny format is undocumented and `agy` marks no tool as read-only, so enforcing it would mean a hand-kept list of tool names. The ping text asks the model to reply briefly and do nothing else (the wake notice asks it to restart the watcher); a model that acts anyway runs one ordinary turn, bounded by `keepwarm_pings`. `agy` also shows Meridian nothing of the prompt box, so a ping can land while the user is typing. A typed `/compact` or `/clear` ends the stretch's pings: `/compact` is read as a return that opens no stretch, and `/clear` is seen when the TUI drops its undocumented `flock` on `presence/<conversation>.lock`. Meridian's own pings and reminders carry `expires_at` (the cache-cold time) in the inbox, so a stale one is dropped instead of reaching a typed turn after a quit and resume.
- **Compaction would beat pinging.** If `agy` gains a way to compact, the state reminder could compact too, and the user would return to a small context with no pings at all.

## Compaction: direction

Not built. The owner chose to bring the state reminder's `compact-now` reply to `agy`, above the reminder itself ([state reminder](../spawns/idle-notifications.md#state-reminder)). The reminder runs; `compact-now` can't, because nothing can compact a running `agy` conversation for the session: only a `/compact` the user types compacts (below). It needs a compact hook reply or a compact tool from Google ([#1049](https://github.com/haowjy/meridian-cli/issues/1049)).

## What `agy` does that Meridian builds on

Probed on the 1.5.15 TUI unless a version is given; recheck after an upgrade. Hook-contract surprises Mars renders around (the `{}` reply, `SessionStart` timing) are under [portable hooks](../mars/package-hooks.md#harness-behavior-to-recheck-after-upgrades).

- **A background command's exit wakes the idle agent** about 35 ms later, after idle gaps from 9 seconds to 62 minutes. The command is a `run_command` with `WaitMsBeforeAsync: 500` and `IsDaemon: false`; the agent sees a `SYSTEM_MESSAGE` with the exit code and stdout. The user can type turns while it runs; the command keeps running and still wakes afterwards. `agy` neither capped nor reaped a watcher at 62 minutes; longer is untested. A command killed from outside does not wake the agent. Esc and `/new` leave background commands running, quitting kills them, and a resumed conversation is told its background tasks stopped. `IsDaemon: true` is untested.
- **`PreInvocation` can't tell a typed prompt from a wake.** Both carry `invocationNum: 0`, the last typed `lastUserInput`, and no source field. The transcript can: a typed prompt appends `USER_INPUT`, a wake `SYSTEM_MESSAGE`.
- **A hook-injected message is in the transcript before the model call it rides on.** `agy` writes the step `PreInvocation` injects when it injects it, so the `[meridian:<id>]` marker is there by the turn's `Stop`, and a turn later cancelled with Esc keeps it too.
- **`Stop.fullyIdle` is false while any background command runs**, so with a watcher up it is always false and says nothing about the turn.
- **A `Stop` reply of `decision: continue` works.** The model sees `Stop hook blocked termination: <reason>` as a `SYSTEM_MESSAGE`, which the TUI does not show the user, and acts on it. `executionNum` is 1 on the `Stop` ending that continuation; `continuationActive` stays false.
- **Esc fires no `Stop`, and `PostInvocation` doesn't fire on a cancelled call.** The transcript has no cancel mark: a cancelled reply leaves a missing step number, a cancelled tool call no result line.
- **The conversation database records each execution's end.** `~/.gemini/antigravity-cli/conversations/<conversation>.db` is SQLite, readable with `mode=ro` while `agy` writes it. Its `executor_metadata` table gains one row when an execution ends; none appeared during a running tool call or a short silent generation, which is why a long think should not read as ended. The row's `data` is a protobuf whose field 1 is the termination reason: 2 (`USER_CANCELED`) after Esc during a reply or a tool call, within 200 ms, and 4 (`NO_TOOL_CALL`) on a normal end. The numbers come from the enum list in the `agy` binary; Google documents none of it, so an upgrade can renumber them.
- **After any Esc, a finished background command wakes nothing until the user types** (twice each for Esc during a reply and during a foreground tool; without Esc the wake came in about 50 ms). The TUI still shows `● Ran` with the command's stdout, so it looks as if the agent was told.
- **A long foreground command ends the turn as a background task.** Asked to run `sleep 20` in the foreground, the model set `WaitMsBeforeAsync: 10000`; after 10 seconds `Stop` fired and the command kept running as `1 task(s)`. A background command is not a running turn: the session counts as idle, and a message for it waits for the watcher.
- **The terminal sandbox (`agy --mode auto`) hides `~/.meridian` and has its own PID namespace**: `~/.meridian` reads as missing, `~/.gemini` is read-only, `/tmp` is visible, and `agy` is PID 1 inside it. A `run_command` with `BypassSandbox: true` runs outside it, which is why the watcher is started that way. The plugin's MCP server already runs outside it.
- **The plugin's MCP tool is unusable on a conversation's whole first turn**, even after a shell call in that turn, though the server process is up within 2 seconds of launch; from the second prompt the model can call it. So the watcher starts through the shell tool, which works on turn one.
- **A native subagent's hooks carry its own conversation ID**, in both `ANTIGRAVITY_CONVERSATION_ID` and the payload.
- **Nothing but a typed `/compact` compacts.** A hook reply injecting `userMessage: "/compact"` (from `PreInvocation` or `PostInvocation`, with any `terminationBehavior`) reaches the model as ordinary text, because slash commands expand only for input the user typed. No model tool compacts. `AGY_CLI_AUTO_COMPACT_OVERRIDE` sets a threshold at launch only, and one below the prompt's base size breaks the turn. A real compaction shows `Compacting conversation…` and adds a `CHECKPOINT` step.
- **Plugin sidecars are read-only UI panes** in the Remote Control view and can't drive a conversation.

## Probing `agy`

- Never run `agy acp` or `agy -p` on Jimmy's personal sign-in. Probe through the TUI in a private tmux server (`tmux -L <spawn id>`), with few, tiny typed prompts.
- Keep a live run under about 25 model turns. A coder's checks once used up the shared Antigravity quota, Jimmy's own, and nothing more could run on it until it reset more than an hour later.
- Run every model turn on `gemini-3.8-flash-low`: launch with `agy --model gemini-3.8-flash-low` and check the TUI shows it. A cache probe is the exception that needs Jimmy's go-ahead: flash-low's cache window is much shorter than Neon's (`gemini-4-neon`, the model in real use), so a flash-low result says nothing about Neon. Flash-low also finishes a no-tool reply in about a second and won't hold a long silent generation, so behavior during a minutes-long think can't be watched live; rest such a claim on what `agy` writes at an execution's end.
- Write nothing into `~/.gemini/config/`, `~/.gemini/antigravity-cli/settings.json` or a real repository. A TUI launch adds its own `trustedWorkspaces` entry. Jimmy's `settings.json` allows `command(meridian)`, and `--settings` rules merge with it rather than replace it, so a probe can't observe the approval prompt a user without that rule gets.
- A scratch project's `.agy/` loads only once `.agents/plugins.json` points at it, and the scratch tree needed `git init`.
- No sign-ins, no `--remote-control`, and never print tokens.
- Most Mars checks need no prompt: `agy plugin validate --strict` on `.agy`, and the files a sync writes.
